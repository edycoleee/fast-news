# M12 — Deployment Production (Scheduler Ops)

## Tujuan

Menetapkan cara menjalankan job operasional (backup dan retention cleanup) **khusus environment production** tanpa menaruh scheduler di aplikasi FastAPI (`run.py`/`main.py`).

## Prinsip

- Scheduler berada di level infrastruktur (host cron / systemd timer / orchestrator), bukan di kode backend.
- Backend tetap stateless untuk request API.
- Job ops dipanggil melalui service profile `ops` pada [docker-compose.prod.yml](/home/ubuntusvr/news-hub/docker-compose.prod.yml).

## Job yang dijadwalkan

1. Backup database:

```bash
docker compose -f docker-compose.prod.yml --profile ops run --rm backup
```

2. Retention cleanup:

```bash
docker compose -f docker-compose.prod.yml --profile ops run --rm cleanup
```

Opsional dry-run (verifikasi):

```bash
docker compose -f docker-compose.prod.yml --profile ops run --rm cleanup python -m scripts.cleanup_security_data --dry-run
```

## Contoh cron production (host)

```cron
# Backup harian 01:30 UTC
30 1 * * * cd /opt/newshub && docker compose -f docker-compose.prod.yml --profile ops run --rm backup >> /var/log/newshub/backup.log 2>&1

# Retention cleanup harian 02:00 UTC
0 2 * * * cd /opt/newshub && docker compose -f docker-compose.prod.yml --profile ops run --rm cleanup >> /var/log/newshub/cleanup.log 2>&1
```

## Kebijakan environment

- Dev/staging boleh manual (tanpa scheduler otomatis).
- Scheduler otomatis diaktifkan hanya pada production.
- Perubahan jadwal mengikuti change approval operasional.

## Verifikasi pasca-aktivasi

1. Log cron menunjukkan exit code sukses.
2. File backup `.dump` dan `.sha256` bertambah sesuai jadwal.
3. Retention cleanup mencatat hasil di audit log (`retention.cleanup`).
4. Restore drill dilakukan berkala sesuai runbook [backup-restore.md](/home/ubuntusvr/news-hub/docs/backup-restore.md).

## Tahapan eksekusi M12 (melanjutkan roadmap)

### Stage 1 — Pre-deployment readiness

Checklist:
- file env production final dan tervalidasi;
- migration `alembic upgrade head` sukses;
- akun admin bootstrap tersedia;
- domain, DNS, dan certificate readiness terkonfirmasi.

Exit criteria:
- `/api/health` dan `/api/readiness` berhasil pada environment target.

### Stage 2 — Production rollout

Langkah:
1. deploy image/container `db`, `backend`, `frontend`, `nginx`;
2. verifikasi dependency antar-service sehat;
3. aktifkan TLS dan redirect HTTP → HTTPS;
4. jalankan smoke test login admin, news list, file access, comment moderation.

Exit criteria:
- semua endpoint kritikal merespons normal melalui HTTPS.

### Stage 3 — Ops automation enablement

Langkah:
1. pasang cron/timer backup harian;
2. pasang cron/timer retention cleanup harian;
3. tentukan lokasi log scheduler dan rotasinya;
4. simpan runbook eksekusi manual untuk fallback.

Exit criteria:
- minimal 1 siklus backup + cleanup berhasil tanpa error.

### Stage 4 — Validation and evidence

Langkah:
1. verifikasi checksum backup;
2. jalankan restore drill ke database restore khusus (bukan production);
3. verifikasi audit trail cleanup;
4. dokumentasikan evidence (timestamp, actor, hasil, checksum, issue/aksi korektif).

Exit criteria:
- restore drill berhasil dan evidence tersimpan.

## Rencana operasional pasca go-live

- **Harian:** cek status scheduler backup/cleanup.
- **Mingguan:** review audit event keamanan penting.
- **Bulanan:** restore drill sampling + review retention value.
- **Perubahan konfigurasi:** wajib change approval dan update dokumen.

## Rollback dan fallback singkat

- Jika scheduler gagal, jalankan job manual via command `ops run --rm`.
- Jika deploy bermasalah, rollback ke image sebelumnya dan ulang smoke test.
- Jika cleanup menimbulkan risiko, jalankan mode `--dry-run` dulu untuk validasi dampak.
